# EPS Prototype: how we work

A next-generation, white-label ticketing platform open to every event organiser, built for the NIBIRU / EPS CTO challenge: a 48-hour prototype, a demo video of at most 5 minutes, and a vision of at most one page. NIBIRU is organiser #1 and is never hard-coded.

Read first, every session: `docs/planning/feature-scope.md` (what we build, with depth), `docs/planning/architecture.md` (22 accepted decisions), `docs/planning/build-plan.md` (the 14 steps, in order) and `docs/planning/spec-map.md` (capability names and conventions). Research is in `docs/research/`; read only the section a change needs.

## Working mode: fully autonomous (the owner's standing instruction)

Claude works on its own through the build plan, one step at a time, with no approval gate between steps:

1. **Propose:** the step's OpenSpec change exists in `openspec/changes/step-<n>-<slug>/`. Bring it up to date with `/opsx:update` if earlier steps changed anything.
2. **Apply:** on a branch `step-<n>-<slug>`, work through `tasks.md` with `/opsx:apply`, ticking each task with its check.
3. **Test locally:** the step's unit and integration tests, then the full suite once.
4. **Open a PR** to `main`. CI runs tests, builds images and deploys a preview: Vercel preview + Neon branch for the web app, and the PR's images on the DOKS cluster for the Go core.
5. **Three adversarial reviewers**, run in parallel as independent sub-agents. Each sees the diff, the change and the specs, but not the others' findings:
   - **Correctness:** tries to break the code against every scenario and edge case (races, expiry, retries, partial failure).
   - **Security and data:** organiser isolation, money and ledger integrity, secrets, auth, bot and abuse paths, GDPR.
   - **Spec and scale:** every scenario met and tested, behaviour under 100k-fan load, failure modes, operability.

   Each reviewer reports findings ranked by severity. Fix every confirmed finding (or record in the PR why it is rejected), then re-run the affected tests.
6. **Test on the deployment:** Playwright against the **deployed preview URL** (desktop and phone, RO and EN where text changed, no console errors, no horizontal scroll), plus API checks against the deployed Go core.
7. **Merge** (standing permission from the owner) only when CI is green, all confirmed review findings are fixed and the deployed tests pass. Squash-merge, then verify the production deploy with a Playwright smoke test.
8. **Archive:** `/opsx:archive` merges the deltas into `openspec/specs/`, adds a `## Status` section to the proposal (what was built, deviations, checks with results) and ticks the step in `docs/planning/build-plan.md`.
9. Next step.

Stop and ask the owner only for: a missing account action (keys, payment, settings), a decision that changes the agreed scope or architecture, or anything destructive (deleting the cluster, database or project, force-pushing to `main`).

**Integrity:** specs and plans may be written before the 48-hour clock; code is written only after the owner says the clock has started.

## Accounts and secrets
- Never commit or print secrets. Never ask for a key in chat.
- **DigitalOcean** API: proxy-injected network secret for `api.digitalocean.com`. Send `Authorization: Bearer proxy-injected`; the proxy replaces it. CI uses the GitHub Actions secret `DIGITALOCEAN_ACCESS_TOKEN`.
- **Neon** and **Vercel**: connectors in the session (MCP tools). CI uses `NEON_API_KEY`. The Neon–Vercel integration sets `DATABASE_URL` per preview.
- **Anthropic** key: only as the Vercel environment variable `ANTHROPIC_API_KEY`, used by the deployed app. Tests use a fake.
- Auth JWT signing keys (EdDSA) are held by Better Auth per Neon branch; Go reads the public keys (JWKS). The rotating-QR and queue-pass keys are generated by CI into Kubernetes secrets.
- Destructive Neon or Vercel actions need the owner's explicit request.

## Product rules
- Open to every organiser; organisers' data is always kept apart.
- Prices shown are all-in; no fee appears first at checkout.
- No real payments: only the simulated providers. No card data is ever handled.
- Sample data (the NIBIRU catalogue) is labelled as sample data.
- EU hosting only (Neon and Vercel functions in Frankfurt, the cluster in Amsterdam). Personal data is per user and deletable.
- AI drafts; it never publishes, buys or sends on its own.
- Romanian and English on fan-facing screens, with correct diacritics.

## Stack (decided)
Next.js (TypeScript, App Router) on Vercel for the control plane. Go for the data plane on DigitalOcean Kubernetes (cluster `eps-prototype-ams3`, Amsterdam, because Frankfurt had no capacity), deployed with Helm. Redis inside the cluster. Postgres on Neon (Frankfurt). Tailwind + shadcn/ui, next-intl, Better Auth. OpenAPI contract between Next.js and Go. Vitest, Playwright, Go tests with testcontainers, k6. Ask before adding a dependency outside this list that is more than a small utility.
