# Design: step 11, AI

## Context

See `proposal.md` for why. The builder (step 2) stores a storefront as versioned theme JSON checked by a schema (U3); the catalogue (step 1) has schemas for events, products, pools and price ladders; publishing compiles a sale snapshot (P1), and only a human action in Studio publishes. Every AI feature here follows U4: drafts, suggestions and links only.

## Goals / Non-Goals

**Goals:**
- A copilot draft that always passes the same validation as a hand-built draft, so the builder can open and publish it with no special case.
- AI never sees or writes another organiser's data, never publishes, never creates holds or orders.
- Deterministic tests: a fake model client replays recorded tool calls.

**Non-Goals:**
- Images generated by AI (the theme uses the brand kit and template imagery), AI pricing or demand forecasting (H4, cut), multi-turn copilot editing of an existing published shop, voice.

## Decisions

### D1 · Model, client and settings
- The Anthropic TypeScript SDK, called only from Next.js route handlers (Node runtime, fra1), key read from `ANTHROPIC_API_KEY`. Model `claude-opus-5-5` for both copilot and concierge (the current default; re-checked against the claude-api reference at build time, and kept in one config constant).
- Adaptive thinking (the model's default), `output_config.effort`: `medium` for the copilot, `low` for the concierge; streaming with `finalMessage()` for the copilot (long tool inputs) and `eager_input_streaming` on its tools, so tool inputs are validated by us (D3).
- Server-side refusal fallback enabled (`server-side-fallback-2026-07-01`, `fallbacks: "default"`); a final `refusal` stop reason is shown as "The copilot could not draft this brief" and nothing is saved.
- Forced tool choice is not available on this model, so `tool_choice` is `auto`, the system prompt names the tools to call, and every tool has `strict: true` with `additionalProperties: false`.
- Typed SDK errors: 429 and 5xx retried by the SDK (2 retries), then a friendly error; timeouts 90 s (copilot) and 20 s (concierge).

### D2 · One model-client interface, a fake in tests
`ModelClient.run(request) → {toolCalls, stopReason, usage}` wraps the SDK. Tests inject `FakeModelClient`, which replays JSON fixtures in `apps/web/tests/fixtures/ai/` (valid draft, invalid-then-repaired draft, refusal, timeout, prompt-injection brief). CI fails if any test constructs the real client.

### D3 · Copilot tools and validation
Tools (all strict JSON schemas generated from the zod schemas of steps 1 and 2):
- `list_templates()` → the four starting templates with their section lists (read-only).
- `get_organiser_context()` → organiser name, brands, currencies, languages, fee policy (read-only, own organiser only).
- `propose_event({event, venue, lineup, dates})`
- `propose_products({products, pools, price_ladders, buying_rules})` (prices in minor units of the shop currency; the fee policy is applied by our code to show all-in prices, never by the model)
- `propose_storefront({template_id, tokens, pages})` (theme JSON)

Each `propose_*` input is parsed with the same zod schema the builder uses, plus cross-checks (every product's pool exists, ladder steps rise, dates in the future, contrast check of B1 on the tokens). A failure returns a `tool_result` with `is_error: true` and the issue list, so the model repairs it; at most 3 repair rounds, then the copilot reports which part failed and saves nothing. When all three parts are valid, one transaction writes a draft event, its draft products and a draft storefront version marked `source=ai` with the brief and model ID. Text fields are plain strings rendered as text, never HTML.

### D4 · No publishing path for AI
The copilot route has no access to the publish or checkout APIs; the publish endpoint requires a signed-in human session with the owner or admin role and an explicit click. The draft banner reads "AI draft: review before publishing". The prompt tells the model it cannot publish; the code makes it impossible either way.

### D5 · Prompt injection and limits
The brief is user data inside a delimited block; the system prompt is fixed and cached. Tools are scoped to the caller's organiser on the server (RLS), so an injected instruction cannot reach other data. Limits: brief ≤ 2,000 characters; 10 copilot runs per organiser per hour; 30 concierge messages per fan session per hour; usage tokens logged per run (no brief text in logs).

### D6 · Concierge
Route `/api/s/<brand>/<shop>/concierge`. Tools: `search_products({query?, day?, max_price?, party_size?})` over that shop's published snapshot only, and `suggest_cart({items:[{product_id, quantity}], note})`. Our code then checks every product exists in the snapshot, quantities are within the per-account cap, and stock is available (existing availability endpoint, no hold), and prices the cart from the snapshot (all-in). The panel shows the itinerary note and an "Add to cart" button that calls the normal cart; checkout, holds and bot rules apply as usual. No chat history is stored beyond the browser session; the panel says "AI suggestion" and works in RO and EN.

### D7 · MCP server
A Next.js route `/api/mcp` with the official TypeScript MCP SDK, Streamable HTTP transport, stateless, no authentication, read-only. Tools:
- `search_events({query?, city?, date_from?, date_to?, max_price?, language?})` → up to 20 published, marketplace-listed events with all-in "from" price and shop URL.
- `get_event({event_id})` → details, products with all-in prices and an availability band (available, low, sold out), never exact stock.
- `create_cart_link({event_id, items})` → a shop URL with a signed cart token (30-minute expiry, `?ref=mcp`) that pre-fills the cart; it creates no hold. The `ref` uses step 10's attribution so MCP sales show as a channel source.
Rate limited per IP (60 calls per minute); no personal data in or out; sample events labelled sample in every result.

## Risks / Trade-offs

- [Model output drifts or a new model changes tool behaviour] → schema validation is the contract, fixtures pin expected behaviour, the model ID is one constant checked at build time.
- [Latency of a full draft (tens of seconds)] → streamed progress steps in the UI ("event", "tickets", "shop"); the demo uses a rehearsed brief.
- [Cost] → effort settings, cached system prompt and tools, per-organiser limits.
- [API outage during the video] → the copilot shows a clear error and the organiser can still build by hand; the recording plan keeps a backup take.
- [MCP abuse or scraping] → read-only public data, rate limits, no stock numbers.
