# Design

## Context

The repository holds only planning documents and OpenSpec. Accounts exist: a Vercel team ("devblocks", `team_pR8jlYM98Wtxqefs0u6pHuXP`, GitHub app installed on the repo, no project yet), a Neon project (`eps-prototype`, `odd-sun-50771070`, aws-eu-central-1, Postgres 18, Neon–Vercel integration that gives each preview its own branch and `DATABASE_URL`) and a DigitalOcean account with no cluster. GitHub Actions has the secrets `DIGITALOCEAN_ACCESS_TOKEN` and `NEON_API_KEY`. The session reaches `api.digitalocean.com` through a proxy that injects the token (`Authorization: Bearer proxy-injected`); it has no database password, so migrations run only in CI. Architecture decisions S1–S3, P2, U1, U2, U5 and R1 (`docs/planning/architecture.md`) are fixed; this document records only the concrete choices they leave open.

## Goals / Non-Goals

**Goals:**
- A green pipeline in which every PR gets a public, working preview of both halves, and `main` is production.
- Isolation by organiser that holds even when application code forgets a filter.
- One sign-in that the Go core trusts without calling back to Next.js on each request.
- Reproducible infrastructure: the cluster and its add-ons can be rebuilt from the repo.

**Non-Goals:**
- Any product screen beyond sign-in and `/status` (organisers, catalogue and builder start in steps 1–2).
- Autoscaling, final resource sizing and k6 (step 12); metrics and dashboards (step 6); the outbox and streams (step 4).
- Custom domains: routing reads the host so they become configuration, but no domain screen (B8 is cut).

## Decisions

### D0.1 Repository and tooling (S1, S2, S3)
- npm workspaces at the root (`apps/web`, plus the existing OpenSpec dev dependency). Node 22 LTS, Go 1.25+.
- `services/` is one Go module (`github.com/<owner>/eps-prototype/services`): `cmd/{gateway,core,worker,fakepsp,simulator}` and `internal/{api,auth,db,tenancy,redisx,health,version}`. Logging with `log/slog` as JSON. HTTP with the standard library router.
- `api/openapi.yaml` (OpenAPI 3.1) is the single contract. TypeScript types with `openapi-typescript` (+ `openapi-fetch` client) into `apps/web/src/lib/core/`; Go strict-server stubs with `oapi-codegen` (std-http target) into `services/internal/api/`. Errors use `application/problem+json` (RFC 9457) with a `code` and a `requestId`. Generated files are committed; CI regenerates and fails on any diff.
- Step 0 endpoints: `GET /healthz`, `GET /readyz` (Postgres and Redis reachable, migrations at the expected version), `GET /v1/version`, `GET /v1/whoami` (verifies the token, echoes its claims). Every binary serves `/healthz` and `/readyz`; the simulator is a Kubernetes Job, disabled by default.

### D0.2 Database: schemas, roles, migrations (P2, U2)
- Migrations are plain SQL run by `pressly/goose`, forward-only: `apps/web/db/migrations/` for `control` and `services/db/migrations/` for `sales`, each with its own version table (`control.goose_db_version`, `sales.goose_db_version`). Better Auth's tables are generated once with its CLI into a control migration.
- Migration `0001` creates two NOLOGIN, NOBYPASSRLS roles: `eps_web` (all on `control`, read on `sales`) and `eps_core` (all on `sales`, read on the `control` tables the core needs: `organisers` and the public-key columns of the auth key table). The branch's connection user is granted both.
- Migration `0004` creates the login roles the applications connect as: `eps_web_login` (member of `eps_web`) and `eps_core_login` (member of `eps_core`), LOGIN, NOBYPASSRLS, no CREATEROLE, owning nothing, without a password in SQL. CI sets a password per branch (`cmd/migrate -login web|core`, which writes the login URLs to a file the job masks): a fresh one per preview push, and the one already in the `eps-db` secret for production, so a rollout never logs the previous release out. The branch owner (`neondb_owner`, a member of `neon_superuser` with BYPASSRLS on Neon) runs migrations only. Raw pool queries such as the schema-version read need only the login role's inherited grants.
- **SECURITY DEFINER rule:** a SECURITY DEFINER function (first: step 3's `control.live_snapshot()`) is owned by a dedicated NOLOGIN NOBYPASSRLS role made for it and sets its own `search_path`; never by the migrating owner, which would bypass RLS. Recorded in spec-map.md.
- Every application transaction begins with `SET LOCAL ROLE eps_web|eps_core` and `select set_config('app.organiser_id', $1, true)`. Tenant tables have `ENABLE` and `FORCE ROW LEVEL SECURITY` with one policy: `organiser_id = nullif(current_setting('app.organiser_id', true), '')::uuid`. With no organiser set a query sees nothing and an insert fails. Fan-facing reads that cross organisers (a public storefront) go through `SECURITY DEFINER` functions or published snapshots that expose only public columns, added by the steps that need them.
- Platform tables without `organiser_id` (users, sessions, auth keys, the organiser registry itself) are listed in one allowlist; a test fails if any other table lacks `organiser_id NOT NULL` or RLS.
- Step 0 creates `control.organisers (id uuid, slug, name, created_at)` and `control.memberships (organiser_id, user_id, role)` so isolation can be tested; step 1 extends them.
- Connections and URLs:
  - Web application queries use the **pooled** URL (`EPS_DATABASE_URL`, else `DATABASE_URL` outside previews): each transaction sets its role and scope with `SET LOCAL`, which a transaction-mode pooler keeps inside the transaction. The opening `BEGIN; SET LOCAL ROLE; set_config(...)` goes out as one statement (ids are validated to `[A-Za-z0-9_-]`), so a transaction costs three round trips, not five.
  - Better Auth uses the **unpooled** URL (`EPS_DATABASE_URL_UNPOOLED`, else `DATABASE_URL_UNPOOLED`; never the pooled one on Vercel): its connections hold a session-level `SET ROLE eps_web; SET search_path TO control`, which a pooler would leak to other clients. If that setup fails the connection is destroyed and the request fails (fail closed); it is never used as the login user.
  - Both web pools are per function instance, reused across requests and bounded (`EPS_DB_POOL_MAX`, default 3).
  - Go uses pgx on the unpooled URL from the namespace's `eps-db` secret (as `eps_core_login`): pods are long-lived and hold their own small pools, bounded per service through Helm (`database.maxConns` → `DB_MAX_CONNS`: core 5, worker 3, 8 per core pod in production), so replicas × bound stays under the Neon compute's limit. The gateway holds no Postgres pool at all.
- Migrations stay forward-only **and backward compatible** (expand, then contract in a later release): a release must run against the schema of the next one, because CI migrates before the rollout and `--atomic` may roll the services back. Readiness therefore requires each schema at **at least** the version the binary expects, not exactly it.

### D0.3 Redis keys (U2)
Every key is built by one Go helper: `eps:{<organiser_id>}:<event_id|_>:<kind>:<rest>`; platform keys use `eps:platform:`. The brace hash tag keeps an organiser's keys together if Redis Cluster arrives later. Hot on-sale keys (holds, stock counters, queues: steps 4 and 5) use `HotKey`, tagged on `{<organiser>:<event>:<shard>}`, so one big sale spreads over many slots while every key still starts with the organiser. Redis in the chart: a small own sub-chart running the official image pinned to an exact tag (`redis:8.4.0`) as a StatefulSet (no Bitnami dependency), AOF off, one replica per environment, `--maxmemory` at about 75 % of the container limit with `noeviction`, so Redis refuses writes before the kernel kills it.

### D0.4 Sign-in and tokens (U1)
- Better Auth in `apps/web` with the magic-link plugin, Google (enabled only when `GOOGLE_CLIENT_ID/SECRET` exist), and the JWT plugin (EdDSA / Ed25519, keys stored in the control schema, private keys encrypted with `BETTER_AUTH_SECRET`, published at `/api/auth/jwks`, rotated every 30 days with the old key kept for 7).
- Signing keys therefore live per database branch rather than as CI-generated Vercel secrets: each preview gets its own keys with no Vercel write from CI. This is a deliberate refinement of the CLAUDE.md line on signing keys; the rotating-QR key (step 7) still comes from CI.
- Core token: `iss` = `urn:eps:web:<env slug>` (the same slug as the core's address: `prod` on main), `aud` = `eps-core`, `sub` = user id or `guest:<id>`, `kind` = `organiser|fan|guest`, `org` (active organiser, organiser tokens only), `role`, `sid`, `jti`, lifetime 5 minutes. Next.js server code gets one per call to Go; the browser can get one from `GET /api/core-token` for direct gateway calls (step 5).
- Go verifies the signature, `iss` (pinned per environment: `CORE_TOKEN_ISSUERS`, default `urn:eps:web:<EPS_ENV>`, so a token from another environment never verifies), `aud`, `exp` (30 s leeway), `kind` and `role` (owner, admin or staff), reading public keys from the control key table through its read grant. Keys live in memory behind a read-write lock and are refreshed in the background every 60 s; an unknown `kid` (a fresh rotation) triggers a reload at most once every 15 s on a limiter of its own, separate from the periodic refresh; concurrent loads collapse into one (singleflight) and no lock is held across the database call. A failed load never locks verification out: after a 1 s back-off the next request loads again. Rejected tokens are counted and logged only at Debug, with the key id cut to 64 characters. Reading from the shared database avoids a callback over Vercel preview protection and keeps each preview's core paired with its own keys.
- Token hot path: a core token costs one database read, the session (always read with the cookie cache off, so a signed-out or revoked session cannot renew a token). The JWKS rows, signing key included, are cached per function instance for 60 s (a key this instance rotates clears it) and memberships for 30 s. Better Auth's session cookie cache (60 s) is on for other reads; the Studio session check, like token issuance, bypasses it.
- Demo identities use the reserved domain `demo.eps.invalid` (RFC 2606: it can never be a real mailbox). A demo-domain user can be created only by the demo buttons or the demo mailbox, and no social account is ever linked to one (database hooks), so an outside Google account cannot take over a demo identity. The shared demo organiser is created race-safely: on a unique violation the request re-reads the user.
- Demo path: when `EPS_DEMO_SIGNIN=on` (previews and the public demo, never by default), `/sign-in` shows "Continue as demo organiser" (one shared demo organiser user, made owner of the sample organiser by step 1's seed) and "Continue as demo fan" (a fresh `demo-fan-<random>` user per click, so visitors never share carts). Rate-limited per IP. Playwright uses these buttons on deployed previews.
- Magic-link mail goes through a sender interface. Without a mail provider key, previews and the demo show the link in an on-screen "demo mailbox" for addresses under the demo domain only, and log nothing sensitive.
- Guests: a signed, httpOnly `eps_guest` cookie with a random id, created on the first buy action; tokens with `kind=guest`. Claiming into an account is step 4 (D8).

### D0.5 Hosting, addresses and previews (R1, I5)
- Vercel project `eps-prototype` (id prj_Wxv6KSuf1LnYTusYGNwtuHdkMXvD, team devblocks; the plan's earlier name `eps-web` was not used), root `apps/web`, functions in fra1, already created through the Vercel connector with Vercel Authentication turned off; it is linked to the repo by the owner in the Vercel UI (or CI deploys with `VERCEL_TOKEN` if the link is missing). Preview deployment protection is turned off so Playwright and interviewers can open previews (they hold no real data). Non-secret env vars set once: `CORE_BASE_DOMAIN`, `EPS_DEMO_SIGNIN`.
- Cluster `eps-prototype-ams3` (DOKS, region ams3 because fra1 had no capacity for small nodes, 1.37.2-do.0, node pool `pool-main` of `s-2vcpu-4gb` autoscaling 2 to 4 nodes; already created on 27 Nov, id 920c7f76-7300-4be7-8210-d8a5cfc9248a) created by `deploy/cluster/up.sh`: idempotent, curl + jq against the DigitalOcean API, token from `DO_TOKEN` (default `proxy-injected` for the session, the Actions secret in CI). Add-ons (Traefik as ingress controller, since ingress-nginx is retired; cert-manager with a Let's Encrypt HTTP-01 `ClusterIssuer`; metrics-server) are installed by `deploy/cluster/addons.sh`, run by the `cluster-bootstrap` workflow because the session may not reach the cluster's API (that workflow is dispatch-only, so until it is on `main` the preview and deploy workflows run `addons.sh` themselves when Traefik is missing).
- Addresses: the Traefik load balancer IP gives `CORE_BASE_DOMAIN = <ip>.sslip.io`. Each environment has a slug: `prod` for `main`; for any other branch `<body>-<6-char sha256 hash of the branch>`, where the body is the branch with every run of characters outside ASCII letters and digits turned into `-` (before lowercasing, so a non-ASCII letter such as `İ` never folds into an ASCII one), lowercased, trimmed, cut to 40 characters, `env` when empty and prefixed `br-` when reserved (prod, main, staging, eps, kube-*). The hash is always added, so no branch can map to `prod` or to another branch's slug (`feature/x`, `feature-x` and `Feature_X` differ). `preview.yml` and `preview-cleanup.yml` take every name from `deploy/scripts/preview-names.sh`, which refuses `main` and anything naming `eps-prod`, and each cluster step checks the namespace again. The core is at `https://core.<slug>.<CORE_BASE_DOMAIN>` and the gateway at `https://gw.<slug>.<CORE_BASE_DOMAIN>`, each with its own cert-manager certificate.
- How a preview finds its core: the web app resolves the core URL at runtime as `CORE_API_URL` if set (production), otherwise from `VERCEL_GIT_COMMIT_REF` through the same slug function. The function is implemented once in TypeScript and once in the CI script, both tested against `deploy/preview-slug-vectors.json`.
- CORS on the core and gateway allows exact origins only: the production web origins (`https://eps-prototype.vercel.app`, the project's production domain, and `https://eps-prototype-devblocks.vercel.app`) and, on a preview, that preview's own Vercel URLs (deployment URL and aliases), which CI reads from the deployment and injects. No wildcard: any Vercel account can name a project so that its URL matches a pattern (a personal project `eps-prototype-evil-devblocks` gets `https://eps-prototype-evil-devblocks.vercel.app`). Residual risk: a preview's core trusts that preview's public URLs, which serve only sample data; the core still requires a token for anything with identity, and CORS never grants credentials.

### D0.6 CI workflows (R1)
- `ci.yml` on every PR and push: web lint, typecheck, Vitest, build; Go vet, test (testcontainers with `postgres:18` and `redis:8`); OpenAPI drift; Helm lint and template; migration dry run against an ephemeral Postgres.
- `preview.yml` on PR open/sync (one concurrency group per PR, `preview-<number>`, shared with the cleanup):
  - build one image per binary (one multi-stage Dockerfile, target per binary) to `ghcr.io/<owner>/eps-<binary>:<sha>` (public packages, no pull secret);
  - **database, never production data:** ensure the seed branch `eps-preview-seed` (created once with Neon's `init_source: "schema-only"` from the default branch, so no row is copied, and with the application schemas then dropped so previews migrate from version 0); recreate `eps-preview/<slug>` as a copy-on-write child of the seed on every push; migrate both schemas; fail unless the user, session and account tables are empty. Step 1 adds the sample-data seed here (sample data only);
  - **web:** wait for Vercel's build of the commit; with `VERCEL_TOKEN`, set `EPS_DATABASE_URL` / `EPS_DATABASE_URL_UNPOOLED` (as `eps_web_login`) scoped to the PR's git branch and redeploy, then use that deployment's exact URLs. On a preview the web app never falls back to the integration's `DATABASE_URL`, which points at a branch copied from production with its data (and whose copied `control.jwks` rows the preview's secret cannot decrypt); without `VERCEL_TOKEN` the preview has no database and the e2e job fails naming the secret;
  - write the core's login URL to the `eps-db` secret in namespace `eps-<slug>`; `helm upgrade --install eps-<slug> --atomic` with the exact CORS origins; wait for readiness and HTTPS; run Playwright against the preview URL. A PR comment lists the web and core URLs.
  - The owner may turn off the Neon–Vercel integration's automatic preview branches (Neon console, integration settings): the pipeline no longer uses them, and each one is a full copy of production.
- `preview-cleanup.yml` on PR close: `helm uninstall`, delete the namespace, delete `eps-preview/<slug>` and the integration's `preview/<branch>` if it exists, and remove the branch-scoped Vercel variables.
- `deploy.yml` on push to `main`: the jobs holding production credentials run in the GitHub environment `production`. Migrate the Neon default branch, build images, write `eps_core_login`'s URL (password kept across deploys) and `helm upgrade --install eps` in namespace `eps-prod`, smoke-test the core, wait for the Vercel production deployment, bind it once to `eps_web_login` (with `VERCEL_TOKEN`) and run the Playwright smoke test. Preview credentials cannot reach `eps-prod`: every preview step checks the namespace, and the owner scopes the preview tokens (PR follow-up).
- `bootstrap-secrets.yml` (manual): generates `BETTER_AUTH_SECRET` per Vercel environment through the Vercel API. It needs a `VERCEL_TOKEN` Actions secret; if that does not exist, the step stops and asks the owner (an account action under CLAUDE.md).

### D0.7 Web app shell (U5)
Next.js App Router with Tailwind and shadcn/ui; next-intl with `ro` (default) and `en`, chosen from a `NEXT_LOCALE` cookie then `Accept-Language`, without a URL prefix for Studio. Middleware reads the host: platform hosts (`*.vercel.app`, `localhost`) route by path; any other host is passed on as a candidate brand domain (resolved in step 3). `/status` shows web version, database schema versions, and the core's `/v1/version` and `/v1/whoami` result.

## Risks / Trade-offs

- [The integration's preview branches copy production data] → CI never uses them: its own branches come from an empty schema-only seed, the web app ignores `DATABASE_URL` on previews, and a pipeline check refuses a preview branch with any user row. The owner may switch the integration's preview branches off.
- [Vercel builds before CI has bound and migrated the branch] → CI redeploys the preview after binding it; the deployed Playwright run uses that deployment.
- [Neon's schema-only branches are root branches, limited per plan] → only the one seed is schema-only; previews are its children.
- [Let's Encrypt rate limits on the shared `sslip.io` domain] → one certificate per environment host, reused across pushes; if issuance is refused, fall back to `nip.io` with the same scheme (one variable change).
- [`SET LOCAL ROLE` forgotten in a code path] → it lives only in the single transaction helper of each side; a test opens a raw connection through the helper and checks `current_user` and that RLS applies.
- [Long branch names breaking DNS labels] → the slug function caps length and is tested on shared vectors.
- [Kubernetes rollouts and drains] → probes time out after 3 s; on SIGTERM readiness turns false, a 5 s `preStop` sleep lets the load balancer drop the pod, then the server drains; PodDisruptionBudgets (`maxUnavailable: 1`); `replicas` is left to the HPA when `autoscaling.enabled`; CPU and memory requests and limits per service with `GOMAXPROCS` from the CPU limit; no server-wide write timeout (per-request deadlines spare server-sent events); `/metrics` on port 9090 outside the ingress; the simulator Job is named per release revision because Job specs are immutable.
- [Load balancer IP changes if the controller is reinstalled] → `CORE_BASE_DOMAIN` is a single Vercel variable and a chart value, updated by `addons.sh` output.

## Migration Plan

Greenfield. Order: Vercel project → cluster and add-ons → first PR (this step) with previews → merge → production. Rollback: `helm rollback` for the core; Vercel instant rollback for the web app; migrations are forward-only and backward compatible (expand now, contract in a later release), so a rolled-back release still runs on the newer schema and a bad migration is fixed by a new one.
